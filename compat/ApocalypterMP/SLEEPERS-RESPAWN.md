## Lifecycle audit — known gaps (2026-10-19)

Source audit requested after commit 069aa72: **do not describe this as fully robust yet**. Normal guest DISCONNECT, quit-to-menu and application quit converge on native OnPeerDisconnected/OnPeerLeft; the clean path attempts a final report/ack first. Crash/network loss reaches the same path when the transport declares disconnection. UDP requires more than 30 seconds without received packets, with host-update stalls compensated; Steam uses ClosedByPeer/ProblemDetectedLocally callbacks. An unresponsive player whose transport still delivers packets has no separate stale-player-state watchdog.

Historical audit before the follow-up above: MultiplayerSleepers.Tick only reconstructed records whose saved ww.sleeping equalled 1. A guest still online at the world's last full save has no sleeping marker, so it will not gain a sleeper merely because the host crashed. Graceful host Stop/Quitting explicitly prevents new sleepers, leaving the same active-guest gap on restart/rehost. Already-saved sleepers return from the loaded world's snapshot; later unsaved movement/guest progress rolls back under Denis's existing world-matching-snapshot policy. Latest standalone checkpoints are intentionally not overlaid on older worlds. A complete fix should reconstruct eligible offline guests from the loaded world's matching records without importing newer player state.

Downed disconnect also needs an explicit state policy: health 1 can be stored and shown as sleeping, but native Survival.IsDowned is not persisted/restored as downed status. Initial/rejected connections without a valid living PlayerRecord intentionally create no body. The original wake path removed the sleeper at PlayerRegistry.GetOrCreate before inventory restoration completed; the follow-up above replaces that path. interrupted join/reconnect and repeated reconnect should be covered by lifecycle tests before claiming transactional recovery. No gameplay tests or source fixes were performed for this audit.

## Behavior and controls

- A departing guest leaves their selected character as a jointed ragdoll labelled `Name - Sleeping`. The label follows the existing Floating names preference and actual rendered camera orientation. Sleepers have no NPC AI, player-presence registration, Health FSM, weapon props, loot or inventory objects. They cannot acquire targets, be revived as online players, or lose the frozen owner's stats to attacks. Their private inventory stays in the existing player record, avoiding duplicate gear on the body.
- Look at a nearby sleeper and press **Use** (normally F) to carry it; press Use again to drop it. The existing Canvas/ItemGrab prompt presents these actions. The host validates distance, line of sight, living/on-foot carrier, availability and one carried sleeper at a time. The host simulates the ragdoll; clients display the host's bone positions/rotations. Entering a vehicle, becoming downed or disconnecting releases the sleeper. This is a new sleeper-specific carry action; native item grab/throw/rotate remains separate.
- On rejoining, the old body is removed once and its latest host position becomes the reconnect destination. Existing native inventory recreation restores the latest host-validated player record: health, hunger/thirst/fatigue, radiation, drunkenness, sanity/insanity, money, flashlight battery, ammo reserves, armor/capacities and saved carried-item variables. Guns' existing WWMagazineRounds/WWMagazineHammer item variables cover per-gun loaded rounds/cocking state. Clean exit still flushes final item/player state and waits for the existing acknowledgment. Connection loss necessarily uses the last reports received by the host, rather than data still only on the disconnected computer. Extra standalone inventories remain outside the existing native loadout coverage.
- **The sleeping body's location and the selected respawn anchor are separate.** Moving/waking the body changes the reconnect destination only. It does not clear or replace `b.item`/the explicit respawn selection. After rejoining, a later death still uses the previously selected sleeping item or seat.
- Hold F to sleep as usual; normal sleep and sleep voting no longer implicitly replace a respawn anchor. Look at a bed, bedroll/sleeping bag or seat and press **Secondary Use** (native `Use_2`, normally E) to select that exact item. The confirmation says `Respawn point set. Previous respawn point replaced.` Native secondary-use actions are suppressed for that press so selection does not also detach the item. Selecting another item replaces the previous selection; there is one active anchor **per player**. Multiple players can select the same item.
- The downed countdown and its automatic give-up deadline are removed. With the existing native DownedEnabled option on, a player can wait for help even when a teammate is outside the old downed-radius check. The normal hold-to-revive control/duration and explicit Give Up control remain. Disabling native DownedEnabled still disables downing.
- Explicit respawn retains native death, inventory drop, corpse announcement and vitals reset. It resolves the selected object's current transform, including a moving vehicle attachment, and searches nearby for a supported, sufficiently level surface with standing-capsule clearance. It does not return to a nearby host, the death location, an old vehicle coordinate or a bed chosen merely by sleeping in it. If the selected item is unavailable/no safe nearby placement is found after 30 seconds, use the initial camp. Main terrain must replace Draft Terrain before control returns. If no safe camp surface is ready, wait with local input frozen rather than release the player into unsupported terrain.
- Initial camp is the host's native `Starter_Area/playerPos`, sent to guests. This is distinct from the native Survival.start field, which could be the guest's joining position. Reconnect placement also checks supported clearance beside the saved sleeper/player position instead of the native terrain-only teleport.
- Each selected sleeping item and its attached vehicle are excluded from native distance deletion, deactivation, distance-kinematic reset and falling-item cleanup. The protected set includes **offline player records**, not just connected peers, and is rebuilt from saved selection metadata after reload. Patrol cleanup and traffic/battle virtualization retain selected vehicles as real objects; the ordinary traffic retirement path prevents duplicate virtual copies. Changing a player's anchor releases that player's old protection; another player's selection can still retain it. Intentional gameplay destruction is not turned into blanket object invulnerability.

## State, authority and lifecycle

`MultiplayerSleepers` uses existing PlayerRecord fields plus `ww.sleeping` and `ww.bodyChoice` stats. Moved body positions are copied into the registry before any checkpoint/world snapshot capture, and a player-only checkpoint is requested every ten seconds while sleepers exist, as well as on drop/disconnect. This does not invoke WorldSaver or a shared saving screen. The ordinary five-minute live-player checkpoint flow remains. Physics proxies and mesh clones are transient objects outside native item/save/reset lists; no components are added to saved game prefabs.

`MultiplayerRespawn` reuses native `b.item`/`b.x/y/z`/`b.lx/ly/lz` fields with explicit `ww.spawnSet`, and stores camp coordinates under `ww.camp.x/y/z`. Sleeping and checkpoint capture preserve those independently of the sleeper position. Old bed records without an explicit selection marker do not silently become new respawn selections. The existing registry and embedded snapshot parsers support these extra stats without a format change.

Every world reload continues to restore its matching embedded `WildWastelandMP.PlayerSnapshot`, including offline sleepers and selected anchors. Newer checkpoint state is not overlaid on an older world. Sleeper position/model/marker persist with that snapshot; the complete physical limb pose is reconstructed rather than saved. Stopping/rehosting the same loaded world retains existing player records as before.

Wire: handshake **17**, unused WW packets 159/160 for reliable full/unreliable sequenced 11-body poses, 161 for reliable removal and 162 for carry/drop intents. Full snapshots repeat every three seconds for joining observers. Removal tombstones reject late pose resurrection. Epoch/host/peer checks guard messages; clients never send arbitrary sleeper transforms. Packet size stays below the existing 1200-byte limit; maximum 512 sleepers. Missing ground freezes host physics until support is loaded; clients remain kinematic.

WW 163 carries initial camp; 164 carries validated exact-anchor requests, acknowledgments and periodic mappings. Native item numbers persist across world reloads, while current network object IDs identify the live replica. Guest objects are named `MP_<prefab>` and lack native `(Clone)<item-number>` suffixes: the host explicitly maps the saved native anchor number to its current network object ID. Do not attempt to parse stable item numbers from guest physical names. Periodic mapping updates do not repeat the selection confirmation.

The PlayerBody config-lifetime SleepingBodies provider supplies the selected skin and existing jointed Ragdoll helper. Normal local death ragdolls retain their original behavior. Modules access the provider through Core Services. New Core hooks use MultiplayerBridge ownership and existing scheduler phases; no new MonoBehaviour loop, UI window, config entry or external DLL changes.

## Source cause/audit

Native `Survival.EnterDowned` sets downedUntil from DownedSeconds, DownedTick calls GiveUp when that expires, and OnGUI renders the remaining seconds. Native CanBeDowned also requires a nearby teammate. Native OnBedConfirmed overwrites HasBed/Bed/BedItem when sleeping. Native DieAndRespawn uses HasBed ? Bed : start, optionally resolves the anchor, then replaces the no-bed guest destination with the host position. Native SafeTeleport.To chooses terrain height without standing clearance. The new hooks target these specific policies; native inventory loss/restore and revival mechanics are retained.

Native NetSession.OnPeerDisconnected runs OnPeerLeft before deleting the remote avatar; existing recovery captures/detaches carried items there. PlayerRegistry.GetOrCreate returns the persistent record before Welcome recreates inventory/builds PlayerRestore, providing the place to update the return position while retaining the sleeper until confirmed spawn. Full-save snapshots already include all offline records. Native DeleteFarAwayItems/DeactivateFarAwayItems use GetDistance; DeleteFallingItems uses DestroyObject. Traffic virtualization requires retiring/detaching retained vehicles instead of merely blocking their eventual Destroy call.
