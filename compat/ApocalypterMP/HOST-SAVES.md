## Preservation / transaction

The established two-phase host barrier remains: freeze all peers, drain edits/hits, flush item/car/player owners, then serialize the host world. Wait for the background player-checkpoint writer before backing up its file. The all-known-player snapshot is embedded in the same cache as the world, including disconnected players and the host; the existing reload-to-matching-player-snapshot rule remains.

The running native file identity is never redirected mid-session. It is a temporary serialization location during the transaction: back up its prior bytes and timestamps, complete native saving and delayed module callbacks, validate and publish a separate named/automatic snapshot, then restore the source file/companions and keep the fresh in-memory world cache. Only an explicit overwrite of the loaded manual source commits that source in place. Guard ES3File.Sync against end-of-frame flushing a protected source outside the host transaction. Settings/non-world files and explicit offline native-slot saves retain their existing paths. The launcher-isolated host/client save directories are respected; recovery runs after launcher path hooks install.

Before any original participant changes, a durable, hash-verified undo journal covers existing and known optional files. The journal is published last, so failed preparation cannot roll back a later successful save. Writes use private staging, hash verification and atomic file replacement where WW publishes files. Existing write timestamps are restored with bytes. Startup rolls back incomplete transactions before hosting. Invalid/unrecoverable journals block hosting/writing and remain on disk. Retry recovery is available in SAVES. Source recovery also discovers newly created slot companions from the interrupted write. Failed native serialization cancels native save FSMs and delayed patrol/SaveBus callbacks before rollback, restores cleanup registrations and requires reload before another write. A confirmed return-to-title-without-saving action remains available after failure; ordinary host disconnect/quit waits for a newly verified exit autosave and cancels exit if saving fails.

Validation reads the persisted transaction marker, required native keys/arrays and player snapshot. Previous ES3 keys must survive, except the exact registered disposable-object keys explicitly selected for cleanup. Unknown/mod/history keys are retained. Module IO errors that were previously swallowed now notify the transaction; native action and disk-commit failures are observed as well.

Participants include the world ES3, native player registry/checkpoint files, screenshot/description, WW per-slot data below config (patrol/traffic/merchant data, NPC senses, POI history, personal/shared host fog, discovered locations, quest crew history), and discovered legacy slot companions in the supported directories. The embedded patrol/quest/per-gun data remain in ES3 with their existing keys/formats. NPC senses' v1 slot header is updated in the staged copy; the loader restores the launcher-selected SaveFile rather than the source identity inside copied globals. SaveBus recognizes the explicitly pending host launch early enough for modules to load MP sidecars/quests before hosting begins.

**Guest personal exploration remains local to that guest**, under the stable world-lineage identity sent by the existing slot reply. It follows Save As/load snapshots without being lost to a filename change; it is not uploaded into the server backup or rolled back with older snapshots. Shared fog and the host's fog/discoveries are server snapshot participants. Standalone extra guest inventories retain their existing MP support limitations (no such inventory mod was installed during this source checkpoint). This feature does not claim new replication support for arbitrary third-party inventories.
